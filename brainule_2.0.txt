

Adaptive Agentic STEM Tutor Platform
Detailed Product and Technical Specification

1. Purpose

Build a fully automated AI tutoring platform for STEM subjects, primarily high school through university level. The system teaches within instructor-defined curriculum boundaries, generates lessons dynamically with LLMs, assesses mastery using randomized unseen quiz items, adapts remediation based on failures, and improves over time through experimentation and analysis.

Primary goals:
- Maximize student success on topic quizzes.
- Minimize the number of wrong answers en route to mastery.
- Minimize frustrating, extended tutoring sessions.
- Keep all instruction inside the approved scope of the course.
- Evolve pedagogy automatically without requiring routine instructor intervention.

The instructor defines what may be taught. The system learns how to teach it.

2. Product Principles

2.1 Curriculum-bounded generation
All lesson content must remain inside an approved course boundary. The root course defines the concept graph, the knowledge corpus, the leaf topics, and the assessment banks. The tutor may rephrase, reorganize, scaffold, and generate new examples and lessons, but only from the approved content universe.

2.2 Assessment separation
The tutor does not know future quiz questions. After a student fails a question, the tutor may receive the failed question, the student response, and grading rationale in order to diagnose the misunderstanding and prepare the student for a different future question in the same leaf-topic scope.

2.3 Mastery-based progression
Progress is based on mastery of leaf topics, not simply on lesson completion. A student advances after answering at least one valid question correctly for each leaf topic. The system may later strengthen this rule, but this is the current baseline.

2.4 Adaptive teaching
The system explores alternative lesson styles, tones, lengths, example densities, visualization usage, and other teaching parameters. It continuously measures what works and shifts toward more effective strategies.

2.5 Fully automated tutoring
Instructors author the root course and define the allowed knowledge boundary. The lesson layer is generated and improved automatically. Instructor intervention should trend toward zero after authoring, aside from occasional root-course refinement.

2.6 Multi-agent operation
The system is implemented as multiple cooperating agents and services with clear contracts, not as one monolithic prompt.

3. Target Use

Subject domain:
- STEM

Learner level:
- High school and above

Tutoring model:
- Fully automated

Expected scale:
- Initial testing on tens of students
- Eventual deployment to tens of thousands or more

Interface model:
- Left panel: topic list and progress
- Center panel: lesson and topic conversation
- Right panel: quiz panel with next-question button

Students may request additional quiz questions on a subtopic from the quiz panel.

4. High-Level System Behavior

For each leaf topic:
1. The system selects a teaching policy.
2. The tutor agent retrieves approved content for the topic.
3. The tutor agent generates a lesson under the selected parameters.
4. The student reads the lesson and may ask topic-scoped questions.
5. The assessment agent selects a random unseen or low-repetition question from the topic bank.
6. The student answers.
7. The grading pipeline evaluates the answer.
8. If correct, the topic is marked mastered.
9. If incorrect, the tutor receives the failed question and error evidence.
10. The tutor generates remediation aimed at the underlying misunderstanding.
11. The assessment agent serves a different question from the same leaf-topic scope.
12. The cycle continues until mastery.

5. System Scope

In scope:
- Instructor-authored root course definition
- Curriculum concept graph
- Approved knowledge corpus, including textbook-derived content
- Randomized per-topic assessment banks
- Dynamic LLM lesson generation
- Dynamic LLM remediation generation
- Student-topic conversation threads
- Multiple question types and visualization guidance
- Logging, analysis, and experimentation
- Multiple LLM providers behind an abstraction layer
- TypeScript implementation portable across Node and Apps Script

Out of scope for initial version:
- Strong security review layer beyond prompt/topic restriction
- Human instructor intervention workflows
- Open-ended unrestricted off-topic assistance
- Heavy synchronous multimedia generation
- Manual pedagogical approvals for each new lesson variant

6. Course Model

The course must be modeled as a directed concept graph with hierarchical organization. A linear chapter list is not sufficient.

Recommended hierarchy:
- Course
- Module
- Unit
- Topic
- Leaf Topic

Only leaf topics are directly assessed for mastery.

A leaf topic should be small enough that a student can receive focused instruction and be assessed with a coherent question bank.

7. Root Course Specification

The root course is the hard boundary for the system. It defines:
- What topics exist
- The prerequisite structure
- Which knowledge artifacts are approved
- Which question banks belong to which leaf topics
- Which misconceptions and learning objectives are associated with each topic
- Which visualization guides and question types are supported

The root course should be human-authored and machine-validated.

8. Recommended Course Content Structure

Each course should contain:
- Course metadata
- Concept graph
- Topic specifications
- Leaf topic specifications
- Knowledge corpus metadata and raw content references
- Misconception library
- Assessment banks
- Visualization guides
- Optional lesson policy defaults

Recommended file layout inside a course package:

- topics/*.yaml

10. Knowledge Corpus Model

The knowledge corpus is the approved raw content universe that the LLM may draw from. It may include:
- textbook excerpts
- derivations
- solved examples
- worked code examples
- diagrams
- formula sheets
- proofs
- explanatory passages

The system should chunk and tag this corpus for retrieval. The tutor may synthesize new lessons from it, but must not pull facts from outside it unless explicitly authorized in a future version.

Recommended corpus strategy:
- Store documents as markdown files where possible.
- Maintain a manifest of document metadata.
- Precompute chunks or use deterministic chunking at runtime.
- Tag chunks by module, topic, leaf topic, difficulty, and document type.

11. Assessment Model

Each leaf topic has an associated bank of quiz questions. Questions are randomly selected on a per-topic basis.

Supported question types should be extensible and each may be paired with visualization guidance.

Initial supported question types may include:
- multiple_choice
- numeric
- symbolic
- short_text
- conceptual_explanation
- diagram_interpretation
- code_execution
- graph_interpretation
- table_interpretation

Assessment expectations and difficulty control should be part of the instructions given to the LLM or grading pipeline administering training, but the bank itself remains the hard topic boundary.

12. Mastery Policy

Current mastery rule:
- A student has mastered a leaf topic when they correctly answer at least one question for that leaf topic.

This is the required baseline behavior.

The system design should keep the mastery policy configurable so it can later support stronger criteria without structural redesign.

Recommended config shape:
- policyId
- type
- minimumCorrect
- requiredQuestionTypes
- requiredDelayCheck

13. Lesson Generation Philosophy

Lessons are not static authored pages. Lessons are dynamic outputs generated by an LLM using:
- the leaf topic definition
- the approved retrieved corpus
- current selected teaching parameters
- student state
- recent failures and misconceptions
- historical performance notes

The lesson should adapt in style, tone, length, and structure based on experimentation and student response.

The LLM should have latitude to generate:
- explanations
- examples
- analogies
- structured walkthroughs
- short guided questions
- visual framing suggestions

It must remain inside the leaf topic scope and the approved corpus.

14. Teaching Parameters

The experimentation system should choose from a bounded variable space of teaching parameters. Initial parameter family examples:
- lessonStyle: definition_first | example_first | analogy_first | misconception_first | procedural_first
- explanationDepth: short | medium | deep
- tone: neutral | encouraging | direct | energetic
- exampleCount: integer range
- socraticRatio: 0.0 to 1.0
- visualizationRatio: 0.0 to 1.0
- stepGranularity: low | medium | high
- prerequisiteRefresh: none | light | moderate | heavy

These are not directly shown to students. They are internal policy variables used to generate lessons.

15. Student Interaction Model

Each leaf topic has an associated conversation thread in the lesson panel. The thread contains:
- generated lesson content
- student questions
- tutor responses

The thread itself is not the object of experimentation. The evolving portion is the lesson-generation strategy and remediation strategy.

The system should allow the student to ask topic-scoped questions within the lesson panel. Off-topic behavior is handled by instruction, not by a heavy security layer in the first version.

26. LLM Abstraction Requirements

The LLM calling layer must be trivial to swap.

Define a provider-agnostic LLM interface in TypeScript.

Recommended interface:

export interface LlmRequest {
  systemPrompt: string;
  userPrompt: string;
  model?: string;
  temperature?: number;
  responseFormat?: 'text' | 'json';
  metadata?: Record<string, unknown>;
}

export interface LlmResponse {
  text: string;
  structured?: unknown;
  raw?: unknown;
  provider: string;
  model: string;
  requestId?: string;
}

export interface LlmClient {
  generate(request: LlmRequest): Promise<LlmResponse>;
}

Adapters should exist for:
- OpenAI
- Anthropic
- Gemini
- Mock LLM
- Any future provider

The core tutoring logic must depend only on LlmClient, never on provider-specific SDKs.

32. Orchestration Flow Specification

The tutoring orchestrator controls the main loop.

Representative flow:
1. Load student state.
2. Determine current leaf topic.
3. Request policy assignment from ExperimentAgent.
4. Retrieve approved content for leaf topic.
5. Load lesson prompt template.
6. Call TutorAgent to generate lesson.
7. Present lesson in center panel.
8. Student optionally asks questions in lesson thread.
9. Student opens or advances quiz panel.
10. AssessmentAgent selects question.
11. Student answers.
12. GradingAgent grades.
13. If correct, mark topic mastered.
14. If incorrect, call FailureAnalysisAgent.
15. Call TutorAgent with remediation prompt and failure evidence.
16. Present remediation.
17. Repeat with a different question.
18. Log all events.
19. Call AnalysisAgent after each cycle.

33. Assessment Serving Rules

Assessment questions must be randomly selected per topic.

Selection rules:
- Must belong to the active leaf topic bank.
- Should avoid immediate repeats.
- Should support a rich buffet of question types.
- May use instructor-defined or system-defined selection weights.
- The next question after a failure should be different from the failed one.

34. Grading Rules

Grading behavior depends on question type.

Possible grading modes:
- deterministic exact match
- numeric tolerance
- symbolic equivalence
- rubric-driven LLM grading
- code execution harness
- hybrid grading

The grading result should be normalized into a common structure regardless of grading method.

35. Remediation Rules

When a student fails a question, the remediation lesson should:
- explain the underlying issue
- use the failed question only as evidence, not as a memorization target
- prepare the student for a different future question in the same topic scope
- stay inside approved content

The remediation prompt should explicitly state that the next question will be a different random item from the same leaf topic.

36. Experimentation Strategy

The system should explore aggressively at low data volumes and gradually exploit better-performing strategies as history grows.

Exploration policy should be configurable.

Examples:
- epsilon-greedy
- contextual bandit
- weighted random by policy score

Initial optimization target:
- maximize quiz success
- minimize number of incorrect attempts before success
- minimize signs of frustration

48. Long-Term Vision

The platform should become a self-improving AI tutor that students love because it consistently teaches well, adapts quickly, remains within scope, and gets students to success with minimal wasted effort.

The end state is not just an LLM that explains topics. It is a curriculum-bounded instructional system that learns, from evidence, which pedagogical approaches work best for which learners and topics.

49. Summary Statement

This system is a curriculum-bounded, multi-agent, self-improving STEM tutoring platform in which instructors define the approved knowledge universe and assessment scope, while LLM-driven lesson generation, remediation, experimentation, and analysis continuously improve how each leaf topic is taught.
